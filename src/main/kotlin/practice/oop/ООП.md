## ЧТО ТАКОЕ ООП И ЕГО ОСНОВНЫЕ ПРИНЦИПЫ?
---
Парадигма программирования, основанная на представлении программы как совокупности объектов, которые содержат данные и поведение и взаимодействуют друг с другом.

Четыре принципа: Инкапсуляция, Наследование, Полиморфизм, Абстракция.

Почему именно эти 4: вместе решают основные проблемы процедурного программирования — дублирование кода, сложность поддержки, отсутствие модульности.

Kotlin — объектно-ориентированный язык с полной поддержкой ООП. Но в отличие от Java, классы и методы в Kotlin по умолчанию final (закрыты для наследования), что стимулирует composition over inheritance.
!!!
## ЧТО ТАКОЕ КЛАСС И КАК ОН ОБЪЯВЛЯЕТСЯ В KOTLIN?
---
Класс — шаблон (blueprint) для создания объектов. Описывает какие данные (свойства) и какое поведение (функции) будут у объекта.

Объявление через ключевое слово class:

```kotlin
class Person(val name: String, var age: Int) {
    fun greet() = "Привет, я $name, мне $age лет"
}

val person = Person("Иван", 25)
println(person.greet()) // Привет, я Иван, мне 25 лет
```

Свойства (properties) — данные класса. val = только чтение, var = чтение и запись:

```kotlin
class Car(
    val brand: String,    // нельзя изменить после создания
    var mileage: Int      // можно изменить
)

val car = Car("Toyota", 50000)
car.mileage = 51000   // OK
// car.brand = "Honda" // ошибка компиляции
```

Класс может быть пустым (без тела):

```kotlin
class Empty
```

Свойства можно объявлять и в теле класса:

```kotlin
class Person(val name: String) {
    var isActive: Boolean = true   // свойство в теле, не в конструкторе
    val nameLength: Int = name.length
}
```

Свойства с кастомными геттерами и сеттерами:

```kotlin
class Temperature(celsius: Double) {
    var celsius: Double = celsius
        set(value) {
            require(value >= -273.15) { "Ниже абсолютного нуля" }
            field = value  // field — backing field, ссылка на хранимое значение
        }

    val fahrenheit: Double   // computed property — нет backing field
        get() = celsius * 9 / 5 + 32
}
```

field (backing field) — специальный идентификатор, доступный только внутри get/set. Это реальное поле, в котором хранится значение свойства. Если свойство не использует field ни в геттере, ни в сеттере — backing field не создаётся (computed property).
!!!
## ЧТО ТАКОЕ КОНСТРУКТОРЫ В KOTLIN?
---
Конструктор — функция, которая создаёт экземпляр класса. В Kotlin два вида: primary (основной) и secondary (дополнительный).

Primary constructor объявляется в заголовке класса:

```kotlin
class Person(val name: String, var age: Int)
```

Если конструктору нужна аннотация или модификатор видимости — ключевое слово constructor обязательно:

```kotlin
class Person private constructor(val name: String)
```

Параметры primary constructor с val/var автоматически становятся свойствами класса. Без val/var — это просто параметры конструктора, доступные только в init-блоках и при инициализации свойств:

```kotlin
class Person(name: String) {        // name — просто параметр, НЕ свойство
    val upperName = name.uppercase() // доступен при инициализации
    // fun getName() = name          // ОШИБКА: name не доступен в методах
}
```

Secondary constructor объявляется в теле класса через constructor. Если есть primary constructor — secondary обязан делегировать к нему через this():

```kotlin
class Person(val name: String, val age: Int) {
    // secondary конструктор делегирует к primary через this
    constructor(name: String) : this(name, 0)

    constructor() : this("Unknown", 0)
}

val p1 = Person("Иван", 25) // primary
val p2 = Person("Анна")     // secondary -> age = 0
val p3 = Person()            // secondary -> name = "Unknown", age = 0
```

Когда нужен secondary constructor:
- Несколько способов создания объекта с разной логикой
- Java-interop (Java не понимает default values)
- Нужна логика до делегации к другому конструктору

На практике в Kotlin secondary constructors нужны редко — default values решают большинство случаев:

```kotlin
// Kotlin-стиль: default values (предпочтительно)
class Person(val name: String = "Unknown", val age: Int = 0)

// Java-стиль: перегрузка конструкторов (избыточно в Kotlin)
class Person(val name: String, val age: Int) {
    constructor(name: String) : this(name, 0)
    constructor() : this("Unknown", 0)
}
```

## ЧТО ТАКОЕ INIT БЛОК И КАКОВ ПОРЯДОК ИНИЦИАЛИЗАЦИИ?
---
init {} — блок инициализации, который выполняется при создании экземпляра. Является частью primary constructor.

```kotlin
class Person(val name: String, var age: Int) {
    init {
        require(age >= 0) { "Возраст не может быть отрицательным" }
        println("Person создан: $name, $age")
    }
}
```

Init-блоков может быть несколько. Они выполняются в порядке появления в коде, чередуясь с инициализаторами свойств:

```kotlin
class Demo(val input: String) {
    val first = "first: $input".also(::println)  // 1

    init {
        println("init 1")                        // 2
    }

    val second = "second: $input".also(::println) // 3

    init {
        println("init 2")                        // 4
    }
}
```

Полный порядок инициализации:
1. Параметры primary constructor вычисляются
2. init-блоки и инициализаторы свойств — сверху вниз, в порядке появления в коде
3. Тело secondary constructor (если вызван secondary)

```kotlin
class Person {
    init {
        println("1. init блок")
    }

    constructor(i: Int) {
        println("2. Secondary constructor: $i")
    }
}

Person(1)
// 1. init блок
// 2. Secondary constructor: 1
```

Даже если нет явного primary constructor, делегация к нему происходит неявно. Поэтому init-блоки ВСЕГДА выполняются до тела secondary constructor.

Порядок инициализации при наследовании (base перед derived):

```kotlin
open class Base(val name: String) {
    init { println("1. Base init") }
    open val size: Int = name.length.also { println("2. Base size: $it") }
}

class Derived(name: String, val lastName: String) :
    Base(name.also { println("0. Arg for base: $it") }) {
    init { println("3. Derived init") }
    override val size: Int =
        (super.size + lastName.length).also { println("4. Derived size: $it") }
}

Derived("hello", "world")
// 0. Arg for base: hello
// 1. Base init
// 2. Base size: 5
// 3. Derived init
// 4. Derived size: 10
```

Важно: при инициализации базового класса свойства наследника ещё не существуют. Если базовый класс вызывает open-метод в init/конструкторе — он может получить неинициализированное значение из наследника. Это частый источник багов.

## ЧТО ТАКОЕ THIS В KOTLIN?
---
this — ссылка на текущий экземпляр класса.

Основное использование — разрешение конфликтов имён:

```kotlin
class Person(name: String) {
    val name: String = name // здесь конфликта нет, но бывает нужно:

    fun setName(name: String) {
        // this.name — свойство класса, name — параметр
    }
}
```

this() — вызов другого конструктора того же класса:

```kotlin
class Person(val name: String, val age: Int) {
    constructor(name: String) : this(name, 0)
}
```

this@label — квалифицированный this для обращения к внешнему контексту из вложенных классов, extension functions и лямбд:

```kotlin
class Outer {                      // implicit label @Outer
    inner class Inner {            // implicit label @Inner
        fun Int.foo() {            // implicit label @foo
            val outer = this@Outer // Outer's this
            val inner = this@Inner // Inner's this
            val receiver = this    // foo()'s receiver (Int)
        }
    }
}
```

Когда нужен this@label:
- inner class обращается к свойствам outer class
- Extension function внутри класса — нужно различить this класса и this receiver'а
- Лямбда с receiver — нужно обратиться к внешнему this

```kotlin
class Button {
    var label = "Click me"

    fun configure() {
        // apply создаёт контекст с this = StringBuilder
        val text = StringBuilder().apply {
            append(this@Button.label) // this@Button — Button
            append(" [OK]")
            // this — StringBuilder
        }
    }
}
```

## ЧТО ТАКОЕ ИНКАПСУЛЯЦИЯ И КАКУЮ ПРОБЛЕМУ РЕШАЕТ?
---
Скрытие внутренней реализации объекта и предоставление контролируемого интерфейса для взаимодействия.

Какую проблему решает:
- Защита данных от некорректного изменения извне
- Сокрытие сложности реализации
- Возможность изменить внутреннюю логику без поломки внешнего кода

Почему важна:
- Снижает связанность кода (loose coupling)
- Упрощает отладку (изменения только через методы)
- Обеспечивает инварианты объекта (гарантии корректного состояния)

Реализация в Kotlin — четыре модификатора видимости:

- public (по умолчанию) — виден отовсюду
- private — виден только внутри класса (для top-level — внутри файла)
- protected — виден внутри класса и в подклассах. НЕ применим к top-level объявлениям
- internal — виден внутри того же модуля (модуль = единица компиляции: Gradle module, Maven project, IntelliJ IDEA module)

Для членов класса:

```kotlin
open class Account {
    private var balance = 0.0        // виден только внутри Account
    protected var interestRate = 0.05 // виден в Account и подклассах
    internal var bankCode = "001"    // виден в том же модуле
    val id = "ACC-001"              // public по умолчанию

    fun deposit(amount: Double) {
        require(amount > 0)
        balance += amount
    }

    fun getBalance() = balance
}

class SavingsAccount : Account() {
    fun addInterest() {
        // balance — не виден (private)
        // interestRate — виден (protected)
        val interest = getBalance() * interestRate
        deposit(interest)
    }
}
```

Для top-level объявлений (функции, свойства, классы на уровне файла):

```kotlin
// file: utils.kt
private fun helper() { }         // видна только в этом файле
internal val config = "..."      // виден в модуле
fun publicApi() { }              // виден отовсюду
// protected — нельзя для top-level
```

Важное отличие от Java: outer class НЕ видит private членов своих inner/nested классов:

```kotlin
class Outer {
    class Nested {
        private val secret = 42
    }

    fun test() {
        // Nested().secret — ОШИБКА: secret is private
    }
}
```

Private setter — свойство можно читать извне, но менять только внутри класса:

```kotlin
class Counter {
    var count: Int = 0
        private set  // setter приватный, getter публичный

    fun increment() { count++ }
}

val c = Counter()
println(c.count)  // OK — чтение через публичный getter
// c.count = 10   // ОШИБКА — setter приватный
c.increment()     // OK — изменение через метод
```

ПРИМЕР: Водителю не нужно знать, как работает двигатель внутри. Он использует руль, педали и приборную панель как интерфейс. Двигатель — private, руль — public.

## ПРИМЕРЫ ИНКАПСУЛЯЦИИ И АНТИПАТТЕРНЫ
---
```kotlin
// БЕЗ инкапсуляции — проблемы
class BankAccountBad {
    var balance = 0.0 // публичное поле
}
// Проблема: кто угодно может сделать account.balance = -1000000

// С инкапсуляцией — решение
class BankAccount {
    private var _balance = 0.0
    val balance: Double get() = _balance  // только чтение

    fun deposit(amount: Double) {
        require(amount > 0) { "Сумма должна быть положительной" }
        _balance += amount
    }

    fun withdraw(amount: Double) {
        require(amount > 0) { "Сумма должна быть положительной" }
        require(amount <= _balance) { "Недостаточно средств" }
        _balance -= amount
    }
}
```

Антипаттерн: публичные var-поля без валидации — теряем контроль над состоянием объекта.

Антипаттерн: геттер, который отдаёт мутабельную коллекцию:

```kotlin
// ПЛОХО — внешний код может менять внутреннее состояние
class Team {
    val members = mutableListOf<String>() // публичный mutable list
}
val team = Team()
team.members.add("Хакер") // обошли инкапсуляцию

// ХОРОШО — отдаём неизменяемую копию
class Team {
    private val _members = mutableListOf<String>()
    val members: List<String> get() = _members.toList()

    fun addMember(name: String) {
        require(name.isNotBlank())
        _members.add(name)
    }
}
```

## ЧТО ТАКОЕ НАСЛЕДОВАНИЕ И КАКУЮ ПРОБЛЕМУ РЕШАЕТ?
---
Создание новых классов на основе существующих, наследуя их свойства и методы.

Какую проблему решает:
- Дублирование кода (DRY)
- Создание иерархий связанных объектов
- Расширение функциональности без изменения базового кода

Почему важно:
- Повторное использование кода
- Логическая организация классов
- Полиморфная замена (подкласс может заменить родителя)

Все классы в Kotlin наследуют от Any. Any предоставляет три метода: equals(), hashCode(), toString(). Это корень иерархии типов.

В Kotlin классы и их члены по умолчанию final — их нельзя наследовать и переопределять. Для разрешения нужно ключевое слово open:

```kotlin
open class Animal(val name: String) {
    open fun sound(): String = "..."
}

class Dog(name: String) : Animal(name) {
    override fun sound(): String = "Гав!"
}

class Cat(name: String) : Animal(name) {
    override fun sound(): String = "Мяу!"
}
```

Правила:
- Класс — open, чтобы от него можно было наследоваться
- Метод/свойство — open, чтобы можно было переопределить
- В наследнике — ключевое слово override
- Сигнатура (имя, параметры, возвращаемый тип) должна совпадать

override-член по умолчанию тоже open. Чтобы запретить дальнейшее переопределение — пометить final:

```kotlin
open class Dog(name: String) : Animal(name) {
    final override fun sound(): String = "Гав!" // дальше переопределять нельзя
}
```

Вызов реализации родителя через super:

```kotlin
open class Shape {
    open fun describe(): String = "Фигура"
}

class Circle(val radius: Double) : Shape() {
    override fun describe(): String = "${super.describe()}: Круг с радиусом $radius"
}

Circle(5.0).describe() // "Фигура: Круг с радиусом 5.0"
```

Переопределение свойств работает так же:

```kotlin
open class Base {
    open val size: Int = 0
}

class Derived : Base() {
    override val size: Int = 42
}
```

val-свойство можно переопределить как var (добавить setter), но var нельзя переопределить как val (убрать setter).

Ограничение: Kotlin поддерживает только одиночное наследование классов. Один класс — один родитель. Для множественного наследования поведения используются интерфейсы.

ПРИМЕР: Легковой автомобиль и Грузовик наследуют базовые характеристики (двигатель, колёса) от Автомобиля, но добавляют свои особенности.

## ПРИМЕРЫ НАСЛЕДОВАНИЯ И АНТИПАТТЕРНЫ
---
```kotlin
// Базовый класс с общей логикой
open class Employee(val name: String, private val baseSalary: Double) {
    open fun calculateSalary(): Double = baseSalary
    fun work() = println("$name работает")
}

// Наследники расширяют функциональность
class Manager(name: String, salary: Double, val bonus: Double) :
    Employee(name, salary) {
    override fun calculateSalary(): Double = super.calculateSalary() + bonus
    fun conductMeeting() = println("$name проводит совещание")
}

class Developer(name: String, salary: Double, val language: String) :
    Employee(name, salary) {
    fun writeCode() = println("$name пишет на $language")
}
```

Антипаттерн: глубокая иерархия наследования (больше 3 уровней) — сложно поддерживать и понимать:

```kotlin
// ПЛОХО — слишком глубоко
open class A
open class B : A()
open class C : B()
open class D : C()
class E : D()

// ХОРОШО — плоская иерархия + интерфейсы для поведения
interface Flyable { fun fly() }
interface Swimmable { fun swim() }

open class Bird(val name: String)
class Duck(name: String) : Bird(name), Flyable, Swimmable {
    override fun fly() = println("$name летит")
    override fun swim() = println("$name плывёт")
}
```

Антипаттерн: наследование ради переиспользования кода, а не ради отношения "is-a":

```kotlin
// ПЛОХО — Stack не является ArrayList
class Stack<T> : ArrayList<T>() {
    fun push(item: T) = add(item)
    fun pop(): T = removeAt(size - 1)
    // но снаружи доступны add(), remove(), get() — это не стек!
}

// ХОРОШО — композиция: Stack СОДЕРЖИТ список
class Stack<T> {
    private val items = mutableListOf<T>()
    fun push(item: T) = items.add(item)
    fun pop(): T = items.removeAt(items.size - 1)
    fun peek(): T = items.last()
    val size: Int get() = items.size
}
```

## ЧТО ТАКОЕ ПОЛИМОРФИЗМ И КАКУЮ ПРОБЛЕМУ РЕШАЕТ?
---
Способность объектов с одинаковым интерфейсом иметь различные реализации. Один и тот же вызов — разное поведение в зависимости от типа объекта.

Какую проблему решает:
- Жёсткая привязка кода к конкретным типам
- Множественные if/when для проверки типов
- Невозможность добавить новые типы без изменения существующего кода

Почему важен:
- Open-Closed принцип (открыт для расширения, закрыт для модификации)
- Упрощение кода через единый интерфейс
- Лёгкое добавление новых типов

Реализация в Kotlin:
- Переопределение методов (override)
- Интерфейсы (interface)
- Абстрактные классы (abstract)

```kotlin
// Полиморфизм через override
open class Shape {
    open fun area(): Double = 0.0
}

class Circle(val radius: Double) : Shape() {
    override fun area() = Math.PI * radius * radius
}

class Rectangle(val width: Double, val height: Double) : Shape() {
    override fun area() = width * height
}

// Функция работает с ЛЮБОЙ фигурой — не знает конкретный тип
fun printArea(shape: Shape) {
    println("Площадь: ${shape.area()}")
}

printArea(Circle(5.0))        // Площадь: 78.53981633974483
printArea(Rectangle(3.0, 4.0)) // Площадь: 12.0
```

Полиморфизм работает через динамическую диспетчеризацию — конкретная реализация метода определяется в runtime по реальному типу объекта, а не по типу переменной:

```kotlin
val shapes: List<Shape> = listOf(Circle(1.0), Rectangle(2.0, 3.0))
shapes.forEach { printArea(it) } // для каждого объекта вызывается своя area()
```

ПРИМЕР: Метод "сигналить" у автомобилей будет разным: легковой — обычный гудок, грузовик — мощный гудок, велосипед — звонок. Но код "подать сигнал для каждого транспорта" не знает конкретный тип.
!!!
## ПРИМЕРЫ ПОЛИМОРФИЗМА И АНТИПАТТЕРНЫ
---
```kotlin
// БЕЗ полиморфизма — проблемный код
fun makeSound(animal: Any) {
    when (animal) {
        is Dog -> println("Гав!")
        is Cat -> println("Мяу!")
        is Cow -> println("Муу!")
        // при добавлении нового животного — менять эту функцию
    }
}

// С полиморфизмом — решение
abstract class Animal(val name: String) {
    abstract fun makeSound(): String
}

class Dog(name: String) : Animal(name) {
    override fun makeSound() = "Гав!"
}

class Cat(name: String) : Animal(name) {
    override fun makeSound() = "Мяу!"
}

class Cow(name: String) : Animal(name) {
    override fun makeSound() = "Муу!"
}

// Функция НЕ меняется при добавлении новых типов
fun printAnimalSound(animal: Animal) {
    println("${animal.name}: ${animal.makeSound()}")
}

// Легко добавить новый тип
class Sheep(name: String) : Animal(name) {
    override fun makeSound() = "Бее!"
}
```

Антипаттерн: when/if по типам вместо полиморфизма. Если добавление нового типа требует изменения существующих when-блоков в нескольких местах — это знак, что нужен полиморфизм.
!!!
## ЧТО ТАКОЕ АБСТРАКЦИЯ И КАКУЮ ПРОБЛЕМУ РЕШАЕТ?
---
Выделение существенных характеристик объекта и сокрытие несущественных деталей реализации. Отвечает на вопрос "ЧТО важно показать?", а инкапсуляция — "КАК спрятать детали?".

Какую проблему решает:
- Перегруженность деталями реализации
- Зависимость от конкретной реализации
- Сложность использования из-за множества методов

Почему важна:
- Упрощает использование сложных систем
- Позволяет фокусироваться на "что", а не "как"
- Снижает когнитивную нагрузку

Реализация в Kotlin — два инструмента: абстрактные классы и интерфейсы.

Abstract class — класс, который нельзя создать напрямую. Может содержать абстрактные члены (без реализации) и обычные (с реализацией):

```kotlin
abstract class Database(val connectionString: String) {
    // Абстрактные — наследник ОБЯЗАН реализовать
    abstract fun connect()
    abstract fun query(sql: String): List<Map<String, Any>>
    abstract fun close()

    // Конкретный — общая логика для всех наследников
    fun isConnected(): Boolean = connectionString.isNotBlank()
}

class PostgresDatabase(connectionString: String) : Database(connectionString) {
    override fun connect() { /* сложная логика PostgreSQL */ }
    override fun query(sql: String): List<Map<String, Any>> { /* ... */ return emptyList() }
    override fun close() { /* ... */ }
}
```

Абстрактный класс и его абстрактные члены — open по умолчанию. Не нужно писать open abstract.

Interface — контракт, определяющий набор функций и свойств без состояния. В отличие от абстрактного класса: нет конструктора, может иметь default implementations, класс может реализовать несколько интерфейсов:

```kotlin
interface Logger {
    fun log(message: String)               // абстрактный — без реализации
    fun warn(message: String) {            // default implementation
        log("WARNING: $message")
    }
}

interface Closeable {
    fun close()
}

class FileLogger(val path: String) : Logger, Closeable {
    override fun log(message: String) = println("[$path] $message")
    override fun close() = println("Файл закрыт")
    // warn() наследуется с default implementation
}
```

Свойства в интерфейсе — можно объявить, но без backing field. Либо абстрактные, либо с кастомным getter:

```kotlin
interface Named {
    val name: String              // абстрактное — наследник предоставит значение
    val upperName: String         // с default getter
        get() = name.uppercase()
}

class User(override val name: String) : Named
```

Разрешение конфликтов при множественном наследовании интерфейсов — если два интерфейса имеют метод с одинаковой сигнатурой и оба дают реализацию, класс обязан переопределить метод и явно выбрать через super<InterfaceName>:

```kotlin
interface A {
    fun greet() = "Привет от A"
}

interface B {
    fun greet() = "Привет от B"
}

class C : A, B {
    override fun greet(): String {
        return "${super<A>.greet()} и ${super<B>.greet()}"
    }
}
```

ПРИМЕР: Для водителя важны скорость и уровень топлива (абстракция), но не молекулярный состав бензина (деталь реализации).
!!!
## ПРИМЕРЫ АБСТРАКЦИИ И АНТИПАТТЕРНЫ
---
```kotlin
// Абстракция хранилища данных
interface Repository<T> {
    fun findById(id: String): T?
    fun save(entity: T)
    fun delete(id: String)
}

// Детали реализации скрыты за интерфейсом
class InMemoryUserRepository : Repository<User> {
    private val storage = mutableMapOf<String, User>()
    override fun findById(id: String) = storage[id]
    override fun save(entity: User) { storage[entity.id] = entity }
    override fun delete(id: String) { storage.remove(id) }
}

class PostgresUserRepository : Repository<User> {
    override fun findById(id: String): User? { /* SQL запрос */ return null }
    override fun save(entity: User) { /* SQL INSERT/UPDATE */ }
    override fun delete(id: String) { /* SQL DELETE */ }
}

// Код использует абстракцию — не знает о деталях хранения
class UserService(private val repo: Repository<User>) {
    fun getUser(id: String) = repo.findById(id)
}
```

Антипаттерн: Leaky abstraction — когда детали реализации просачиваются наружу:

```kotlin
// ПЛОХО — абстракция "протекает": метод выдаёт деталь реализации
interface Cache {
    fun get(key: String): String?
    fun set(key: String, value: String)
    fun getRedisConnection(): Any  // протечка! потребитель не должен знать что это Redis
}

// ХОРОШО — чистая абстракция
interface Cache {
    fun get(key: String): String?
    fun set(key: String, value: String)
    fun clear()
}
```
!!!
## ЧЕМ ABSTRACT CLASS ОТЛИЧАЕТСЯ ОТ INTERFACE?
---
Конструктор:
- Abstract class — ЕСТЬ. Может принимать параметры и инициализировать состояние
- Interface — НЕТ. Не может иметь конструктор

Состояние (backing fields):
- Abstract class — МОЖЕТ хранить состояние (val/var с backing field)
- Interface — НЕ МОЖЕТ. Свойства только абстрактные или с кастомным getter (без field)

Наследование:
- Abstract class — одиночное. Класс наследует только один abstract class
- Interface — множественное. Класс реализует сколько угодно интерфейсов

Модификаторы видимости:
- Abstract class — может иметь private, protected, internal, public члены
- Interface — члены public по умолчанию. private — можно (Kotlin 1.4+), protected и internal — нельзя

Default реализации:
- Abstract class — может иметь и abstract и обычные методы
- Interface — может иметь default implementations для методов

```kotlin
// Abstract class — когда есть общее состояние и конструктор
abstract class Vehicle(val maxSpeed: Int) {
    var currentSpeed = 0
        protected set

    fun accelerate(amount: Int) {
        currentSpeed = minOf(currentSpeed + amount, maxSpeed)
    }

    abstract fun fuelType(): String
}

// Interface — когда нужен контракт без состояния
interface Electric {
    val batteryLevel: Int  // абстрактное свойство
    fun charge()
}

// Класс комбинирует оба
class Tesla : Vehicle(250), Electric {
    override var batteryLevel = 100
        private set

    override fun fuelType() = "Электричество"
    override fun charge() { batteryLevel = 100 }
}
```

Когда использовать abstract class:
- Есть общее состояние (поля с данными), которое разделяют все наследники
- Нужен конструктор с параметрами
- Тесная связь "is-a" (Dog is an Animal)

Когда использовать interface:
- Определяешь контракт — набор возможностей ("can-do")
- Нужна множественная реализация
- Нет общего состояния между реализациями
- Слабая связь — разные классы реализуют одно поведение (Printable, Serializable)

На практике: начинай с interface. Если появляется общий код с состоянием — выноси в abstract class.
!!!
## ЧТО ОТЛИЧАЕТСЯ В ООП KOTLIN ОТ DART?
---
Для тех, кто знает Dart — ключевые отличия:

- Kotlin: классы и методы final по умолчанию (нужен open). Dart: всё наследуемое по умолчанию (нужен final/sealed в Dart 3)
- Kotlin: 4 модификатора видимости (public, private, protected, internal). Dart: приватность через префикс _ на уровне библиотеки, нет protected/internal
- Kotlin: нет множественного наследования классов, но есть интерфейсы с default methods. Dart: нет множественного наследования, но есть mixins (with)
- Kotlin: нет mixins как концепции. Аналогичная задача решается через интерфейсы с default implementations
- Kotlin: есть перегрузка методов (overloading — одинаковое имя, разные параметры). Dart: нет перегрузки — используются именованные параметры
- Kotlin: abstract class может иметь конструктор. Dart: abstract class тоже может иметь конструктор
- Kotlin: каждый класс НЕ является неявным интерфейсом. Dart: каждый класс = неявный интерфейс (implements любой класс)
- Kotlin: override — ключевое слово. Dart: @override — аннотация (рекомендация, не требование компилятора; в Dart 3 строже)
!!!
## АНТИПАТТЕРНЫ ООП
---
1. God Object — класс, который знает и делает слишком много:

```kotlin
// ПЛОХО
class UserManager {
    fun createUser() { }
    fun validateEmail() { }
    fun sendEmail() { }
    fun saveToDatabase() { }
    fun generateReport() { }
    fun formatCsv() { }
}

// ХОРОШО — разделить по ответственности
class UserService { fun createUser() { } }
class EmailValidator { fun validate(email: String) { } }
class EmailSender { fun send(to: String, body: String) { } }
class UserRepository { fun save(user: User) { } }
```

2. Наследование вместо композиции:

```kotlin
// ПЛОХО — использование наследования для переиспользования кода
open class Logger { fun log(msg: String) { } }
class UserService : Logger() { // UserService IS-A Logger? Нет.
    fun createUser() { log("creating user") }
}

// ХОРОШО — композиция
class UserService(private val logger: Logger) {
    fun createUser() { logger.log("creating user") }
}
```

3. Нарушение инкапсуляции через мутабельные коллекции (см. раздел "ПРИМЕРЫ ИНКАПСУЛЯЦИИ")

4. Вызов open-методов в конструкторе базового класса:

```kotlin
// ОПАСНО — override свойство ещё не инициализировано
open class Base {
    init {
        println(name()) // вызывает override версию!
    }
    open fun name() = "Base"
}

class Derived : Base() {
    private val label = "Derived"
    override fun name() = label // label ещё null в момент вызова из Base.init!
}

Derived() // напечатает: null
```

5. Пустые override-методы (нарушение контракта):

```kotlin
// ПЛОХО — нарушение LSP
open class Bird {
    open fun fly() = println("Летит")
}

class Penguin : Bird() {
    override fun fly() { /* ничего не делает */ } // нарушение контракта
}
```
